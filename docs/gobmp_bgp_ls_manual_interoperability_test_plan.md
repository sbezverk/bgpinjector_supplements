# Manual BGP-LS Interoperability Test Plan for GoBMP

## Purpose

This plan defines a repeatable, evidence-based process for checking BGP-LS
advertisements generated by `bgpinjector` and decoded by GoBMP through an IOS
XR BMP connection. It is designed for manual execution in the XRd testbed first,
then for conversion into automated validation.

The main diagnostic goal is to identify which boundary loses or changes a
field. BMP Route Mirroring carries copies of messages from the monitored BGP
session; see [RFC 7854, Sections 3.1, 4.7, and 6](https://www.rfc-editor.org/rfc/rfc7854.html#section-4.7):

```text
fixture JSON -> bgpinjector -> BGP UPDATE -> IOS XR -> BMP Route Mirroring
             -> embedded BGP UPDATE -> GoBMP decoded record
```

An HTTP response from `bgpinjector` confirms that the request was accepted and
queued. It does not prove that XR received the UPDATE, that the route entered
the BGP table, or that GoBMP decoded the corresponding BMP message. Each of
those stages has a separate verification step below.

## Scope and assumptions

- The procedure uses the GoBMP-focused, POST-ready BGP-LS fixtures in
  `injection_cases/gobmp/bgp_ls/`. The general bgpinjector API examples are in
  `injection_cases/bgp_ls/`; use those when testing an API case not included in
  the GoBMP-focused set. The ordinary IPv4-unicast control fixture is
  `injection_cases/gobmp/ipv4_unicast_route.json`.
- The example testbed is `testbeds/bgp_ls/docker-compose.yml`.
- All paths in this plan are relative to the root of the public
  `bgpinjector_supplements` repository.
- In that testbed, the injector API is published on host port `18080`, GoBMP
  listens on `192.168.100.10:5000`, and the RR1-to-injector test link uses
  `192.0.2.1` / `192.0.2.2` and `fd00:100::1` / `fd00:100::2`.
- The current XR behavior under test disables BMP Route Monitoring for BGP-LS
  AFI/SAFI. Configure and verify BMP Route Mirroring for the relevant peer
  using the syntax supported by the tested XR release. Do not treat the lack of
  a Route Monitoring message as a GoBMP decoding failure in this setup.
- Keep the BGP-LS session and BMP transport healthy throughout a run. Record
  the transport address family; it is distinct from the route AFI/SAFI.
- Run one fixture at a time. Avoid reusing the same NLRI unless the previous
  route has been withdrawn or the run is explicitly testing an update to an
  existing route.
- The XRd/GoBMP Compose project may run on a remote Linux server while the
  operator works from a workstation. The preferred examples below keep the
  evidence bundle and `curl` request on the workstation and use SSH to run
  remote commands or stream artifacts. An interactive shell on the server is
  not required. The operator needs suitable SSH command access, or help from
  the server administrator to provide the GoBMP logs and JSONL output. A
  packet capture additionally requires capture privileges and is optional.

## Workstation and test server setup

Clone the public supplements repository on the workstation if it is not
already present:

```sh
git clone https://github.com/sbezverk/bgpinjector_supplements.git
```

The repository keeps the related materials together:

```text
bgpinjector_supplements/
├── docs/                         test plan and user guide
├── injection_cases/
│   ├── bgp_ls/                   general BGP-LS API examples
│   └── gobmp/bgp_ls/             GoBMP-focused BGP-LS cases for this plan
└── testbeds/bgp_ls/              Compose topology, XR configs, and output/
```

The test server also needs a checkout of this repository because the Docker
Compose project and its bind-mounted output directory live there. If the server
already has a checkout, set `LAB_DIR` below to its root. Otherwise, clone the
repository from the workstation over SSH after creating the run-context file.
Use the same published repository revision on both systems. The run setup
below records both checkout revisions in the manifest.

Create one workstation run-context file for the test. Each terminal session
will source the same file, so the fixture and evidence paths stay consistent.
Use a readable `RUN_LABEL` with a sequence number for repeated attempts; record
the UTC start time in the manifest rather than in the directory name.

```sh
RUN_CONTEXT_DIR="{path to the existing runtime environmen folder}/run.env"
RUN_CONTEXT="$RUN_CONTEXT_DIR/bgp-ls-run.env"  
cat > "$RUN_CONTEXT" <<'EOF'
REPO_DIR="{path to the local bgpinjector supplements repo}"
RUN_CONTEXT_DIR="{path to the existing runtime environmen folder}/run.env"
RUN_CONTEXT="$RUN_CONTEXT_DIR/bgp-ls-run.env"
FIXTURE_DIR="$REPO_DIR/injection_cases/gobmp/bgp_ls"
FIXTURE_NAME="link_isis_attributes.json"
LAB_HOST="sbezverk@10.225.253.186"
LAB_DIR="{path to bgpinjector supplements repo on a server running test bed setup}"
RESULTS_DIR="$RUN_CONTEXT_DIR/results"
RUN_LABEL="link-isis-attributes-run-01"
EOF
```

If the server does not already have the repository checkout, create it now:

```sh
ssh "$LAB_HOST" "git clone https://github.com/sbezverk/bgpinjector_supplements.git '$LAB_DIR'"
```

In every terminal session, source that same file and derive the fixture and
run paths:

```sh
RUN_CONTEXT="/absolute/path/to/bgp-ls-run.env"
source "$RUN_CONTEXT"
FIXTURE_PATH="$FIXTURE_DIR/$FIXTURE_NAME"
RUN_DIR="$RESULTS_DIR/$RUN_LABEL"
```

Run this initialization once per fixture attempt, not once per terminal. It
creates the evidence directory, copies and hashes the exact fixture, and
records the fixture identity:

```sh
mkdir -p "$RUN_DIR"
test -f "$FIXTURE_PATH"
cp "$FIXTURE_PATH" "$RUN_DIR/fixture.json"
shasum -a 256 "$RUN_DIR/fixture.json" > "$RUN_DIR/fixture.sha256"
printf 'fixture_name=%s\nfixture_path=%s\n' \
  "$FIXTURE_NAME" "$FIXTURE_PATH" \
  > "$RUN_DIR/manifest.txt"
printf 'workstation_repo_commit=%s\n' \
  "$(git -C "$FIXTURE_DIR" rev-parse HEAD)" \
  >> "$RUN_DIR/manifest.txt"
printf 'server_repo_commit=%s\n' \
  "$(ssh "$LAB_HOST" "git -C '$LAB_DIR' rev-parse HEAD")" \
  >> "$RUN_DIR/manifest.txt"
```

The test server's `LAB_DIR` is the root of its `bgpinjector_supplements`
checkout, which contains `testbeds/bgp_ls/docker-compose.yml`. It can be a
different clone from the workstation checkout, but use the same commit on both
systems. For a later attempt, update `FIXTURE_NAME` and `RUN_LABEL` in the
context file, then source it again in each terminal. For a general API fixture,
set `FIXTURE_DIR` to
`/path/to/bgpinjector_supplements/injection_cases/bgp_ls`; for the IPv4-unicast
control, set it to
`/path/to/bgpinjector_supplements/injection_cases/gobmp`.
Choose a new label so previous evidence is preserved.

Keep the SSH tunnel open in a separate workstation terminal while injecting:

```sh
ssh -N -L 18080:127.0.0.1:18080 "$LAB_HOST"
```

The rest of the test uses `http://127.0.0.1:18080/v1/routes` from the
workstation. If the lab already exposes the API on a trusted network, the
operator may use that reachable address instead. The tunnel avoids requiring
the injector API to be reachable directly from the workstation.

All evidence files are written under the workstation's `RUN_DIR`. Testbed
commands use SSH to execute on the Linux server, and output files are streamed
or copied back to the workstation. If SSH command execution is unavailable,
ask the server administrator to provide the GoBMP JSONL snapshot, logs, and
pre-decode hex dumps for the recorded UTC interval. If those dumps are
incomplete, request a BMP packet capture too. The test can still be reviewed,
but the operator cannot independently collect wire evidence.

## Testbed preparation

From the workstation, confirm the testbed services and images through SSH:

```sh
ssh "$LAB_HOST" "cd '$LAB_DIR' && docker compose -f testbeds/bgp_ls/docker-compose.yml ps" \
  > "$RUN_DIR/compose-ps.txt"
ssh "$LAB_HOST" "cd '$LAB_DIR' && docker compose -f testbeds/bgp_ls/docker-compose.yml images" \
  > "$RUN_DIR/compose-images.txt"
```

Start only services that are stopped. Starting all XRd containers can consume
substantial memory and CPU:

```sh
ssh "$LAB_HOST" "cd '$LAB_DIR' && docker compose -f testbeds/bgp_ls/docker-compose.yml up -d gobmp bgpinjector" \
  > "$RUN_DIR/compose-up.txt"
```

Verify the following before injecting:

1. The BGP session between bgpinjector and RR1 is established.
2. BGP-LS AFI 16388 / SAFI 71 is negotiated on that session.
3. RR1's BMP connection to GoBMP is established.
4. Route Mirroring is enabled for the monitored BGP peer and the intended
   direction. Record the exact XR configuration and XR software release.
5. GoBMP starts with file output enabled. The example Compose service writes
   JSON Lines to `testbeds/bgp_ls/output/gobmp.jsonl` using `--dump=file`
   and `--msg-file=/output/gobmp.jsonl`. The path is relative to the Compose
   file's directory on the server. It also runs at
   verbosity 9, which includes pre-decode BMP hex dumps for Route Monitoring
   and Route Mirroring messages.

Capture version and configuration evidence once per test session:

- XR `show version` output for RR1.
- `docker compose ... images` output and image tags/digests for bgpinjector and
  GoBMP.
- bgpinjector startup log banner/version and its peer/session details.
- GoBMP startup arguments, logs, and BMP listen address.
- Sanitized RR1 BGP, BMP, and Route Mirroring configuration relevant to the
  monitored peer.

Do not publish license data, credentials, tokens, serial numbers, internal
hostnames, or unrelated production configuration. The fixtures use lab and
documentation addresses; replace any environment-specific values before
publishing a run bundle.

## Evidence directory and run manifest

Use the `RUN_DIR` created in the workstation setup section for this fixture.
Set a new `RUN_LABEL` and derive a new `RUN_DIR` for each subsequent fixture
attempt.

Store the following in each run directory:

```text
manifest.txt                  run label, UTC start/end, operator, versions
fixture.json                  exact request body used
http-headers.txt              HTTP status and headers
http-response.txt             HTTP response body
xr-before.txt                 session, BMP, and relevant route state before
xr-after.txt                  received route detail and BMP state after
gobmp.log                     GoBMP pre-decode hex dumps and logs
gobmp-all.jsonl               GoBMP decoded output snapshot
bmp-route-mirror.pcap         optional BMP TCP capture, including mirrored PDU
bgp-peer.pcap                 optional BGP TCP capture on port 179
expected-vs-observed.md       field-by-field comparison and conclusions
```

The fixture copy and its SHA-256 are created during workstation setup. Record
the exact injection command and UTC collection time in the run manifest.

Do not truncate GoBMP's output file while its process is writing to it. For
this two-host workflow, copy the complete JSONL file after each fixture and
filter it on the workstation by timestamp, peer, and NLRI. Do not restart
GoBMP mid-run unless the restart itself is being tested.

## Per-fixture procedure

### 1. Record the baseline

Before injection, save the relevant XR and GoBMP state:

- BGP neighbor state and negotiated AFI/SAFI.
- RR1 BMP server state and the Route Mirroring configuration for the peer.
- Whether the intended NLRI already exists in the BGP-LS table.
- GoBMP log and JSONL output baseline.
- UTC timestamp.

Record a UTC timestamp before injection in the manifest. The GoBMP log
capture uses `--tail=0 --follow`, so it does not need this variable in its
terminal session. Use the route's timestamp, peer, and NLRI when filtering the
copied JSONL file locally.

```sh
START_UTC=$(date -u '+%Y-%m-%dT%H:%M:%SZ')
printf 'start_utc=%s\n' "$START_UTC" \
  >> "$RUN_DIR/manifest.txt"
```

Use the XR release's supported commands. Typical useful views include BGP
neighbor detail, `show bgp bmp server 1 detail`, and a BGP-LS table query for
the exact NLRI. Save the full output rather than only a screenshot or a
paraphrase.

If the same NLRI already exists, withdraw it and verify its removal before the
test, or use a fixture whose NLRI is unique to this run. Do not clear a shared
production or lab table as a shortcut.

### 2. Capture GoBMP's pre-decode hex dump

The example GoBMP Compose service uses `--v=9`. At verbosity 6 and above,
GoBMP logs the BMP common header, per-peer header, and Route Monitor or Route
Mirror message body as hex before parsing that body. The decoder logs the body
before it unmarshals Route Mirroring TLVs or the embedded BGP PDU. Collect the
GoBMP log from the workstation over SSH:

```sh
ssh "$LAB_HOST" \
  "cd '$LAB_DIR' && docker compose -f testbeds/bgp_ls/docker-compose.yml logs --no-color --follow --tail=0 gobmp" \
  > "$RUN_DIR/gobmp.log"
```

Start this command in a workstation terminal before injection. Run the
injection in another terminal, then stop log following with Ctrl-C after the
decoded record appears or the test times out. The log file is created on the
workstation.

For each relevant message, retain the adjacent log entries for:

- `BMP CommonHeader Raw` — six-byte header; byte 5 identifies the BMP wire
  message type (0 Route Monitoring or 6 Route Mirroring).
- `BMP Per Peer Header Raw` — peer identity, peer type, and flags.
- `BMP Route Monitor Message Raw` or `BMP Route Mirror Message Raw` — the
  message body passed to the corresponding decoder.

The Route Monitor body is the embedded BGP PDU. The Route Mirror body starts
with its TLVs; TLV type 0 contains the embedded BGP PDU. Thus a hex line that
starts with `00 00 00 ...` is the Route Mirror body, not the entire outer BMP
frame. The common and per-peer header logs identify the BMP type and peer and
are required to reconstruct the full frame. Correlate the three entries by
timestamp and order in the same GoBMP log stream. GoBMP may log the common
header more than once; verify the association by length as well: the common
header's total message length must equal 6 bytes plus the 42-byte per-peer
header plus the logged body length.

These logs are enough for field-level comparison when all three parts are
present and untruncated. Keep the original log text as well as the decoded
JSONL record. If a hex dump is missing, truncated, or ambiguous, use a PCAP as
the fallback or ask the server administrator to capture it.

### Optional: capture the BMP or BGP TCP stream

A packet capture is optional when the GoBMP log has the complete common
header, per-peer header, and body. Use a PCAP if the logs are incomplete, TCP
delivery/reassembly is in question, or an independent wire artifact is needed.
The BMP capture can be streamed over SSH to the workstation:

```sh
ssh -T "$LAB_HOST" \
  "sudo -n tcpdump -i any -nn -s 0 -U -w - 'host 192.168.100.10 and tcp port 5000'" \
  > "$RUN_DIR/bmp-route-mirror.pcap"
```

The remote account must be allowed to run `tcpdump` non-interactively with
`sudo -n`; otherwise, ask the server administrator to collect the capture.

For additional separation of responsibilities, an optional second capture on
the injector-to-RR BGP link can verify the UPDATE sent toward XR:

```sh
ssh -T "$LAB_HOST" \
  "sudo -n tcpdump -i any -nn -s 0 -U -w - 'host 192.0.2.1 and host 192.0.2.2 and tcp port 179'" \
  > "$RUN_DIR/bgp-peer.pcap"
```

If the lab uses different addresses, update the filters. Preserve the full
capture; a short terminal dump may omit the exact TLV bytes needed to classify
a discrepancy.

### 3. Inject exactly one fixture

From the workstation, send the already-copied fixture through the SSH tunnel
and save the request response:

```sh
curl --fail-with-body -sS -D "$RUN_DIR/http-headers.txt" \
  -X POST http://127.0.0.1:18080/v1/routes \
  -H 'content-type: application/json' \
  --data-binary @"$RUN_DIR/fixture.json" \
  -o "$RUN_DIR/http-response.txt"
```

Replace the filename for each fixture. Save the response even when the request
fails. Record the `curl` command in `manifest.txt`. An accepted/queued response
is only the first checkpoint; continue with the RR and GoBMP checks.

After the route appears or the test times out, copy GoBMP's JSONL output from
the server. The pre-decode hex logs were collected in the previous step. No
line count or local server-side editing is needed:

```sh
scp "$LAB_HOST:$LAB_DIR/testbeds/bgp_ls/output/gobmp.jsonl" \
  "$RUN_DIR/gobmp-all.jsonl"
```

Keep `gobmp-all.jsonl` unchanged as collected evidence. Create a filtered copy
locally for review, using the test timestamp, peer, and NLRI. Record whether
GoBMP was restarted during the run because that may have recreated its output
file.

### 4. Verify reception by XR

After the injection, save XR output on the workstation showing:

- The peer remains Established and BGP-LS remains negotiated.
- The exact NLRI is present in the expected BGP-LS table and has the expected
  protocol, instance ID, descriptors, and route type.
- The received path attributes that XR displays, including values under test.
- No malformed UPDATE notification or session reset occurred.
- BMP Route Mirroring remains active for the relevant peer.

If the route is absent, stop the decoder investigation here. First establish
whether the BGP UPDATE reached XR and whether XR rejected, treated-as-withdraw,
or discarded it. Preserve any XR malformed-update diagnostics.

### 5. Verify GoBMP output

Save the GoBMP JSON records produced after the injection and the matching log
interval. Select records by timestamp, peer, AFI/SAFI, and NLRI rather than by
`msg_type` alone.

GoBMP's JSON `msg_type` is an application record category, not the BMP wire
message type. For example, an IPv4-unicast record category and a BGP-LS Link
record category describe decoded output. BMP Route Mirroring is wire message
type 6. End-of-RIB records and statistics records are separate output records;
they are not evidence of an additional BGP-LS route.

For BGP-LS, verify at least:

- Expected GoBMP NLRI category: Node, Link, Prefix, SRv6 SID, or SR Policy.
- Protocol ID, instance/domain ID, and local/remote node descriptors.
- Link or prefix descriptors, including address families and MT-ID where
  applicable.
- Attributes relevant to the fixture, including repeated values and nested
  TLVs.
- Peer identity and next hop. Do not confuse the BGP peer transport address
  family with the NLRI AFI/SAFI or the BGP next-hop address family.
- Action (add/withdraw), timestamp, path identity when applicable, and any
  relevant Route Mirroring loss/error information.

A negotiated BGP-LS capability in the Peer Up OPENs confirms AFI/SAFI support,
but it does not prove a BGP-LS route was mirrored. For that, find the expected
NLRI in an actual Route Monitor or Route Mirror BGP UPDATE body.

If the Route Mirroring message contains an error or Messages Lost indication,
mark the run as incomplete for field-by-field route coverage. Keep the capture
and decoded records, but do not treat a missing route after a reported loss as
a decoder defect until the test is repeated without that condition.

### 6. Compare expected values with wire and decoded output

Create a field table in `expected-vs-observed.md`:

| Field / TLV | Fixture input | BGP UPDATE in BMP capture | GoBMP output | Result |
|---|---|---|---|---|
| Example: shared risk groups | `[101, 202]` | list TLV bytes | `[101]` | decoder or encoder investigation |

For every discrepancy, answer these questions in order:

1. Did bgpinjector accept the intended JSON value?
2. Is the field encoded in the UPDATE sent from bgpinjector to XR?
3. Is the field still present in the BGP UPDATE embedded in the BMP Route
   Mirroring message sent by XR?
4. Does the embedded TLV have the RFC-defined type, length, byte order, and
   value format?
5. Does GoBMP publish the same semantic value, a documented normalization, or
   an incorrect/missing value?

Classify the result only after these checks:

| Evidence | Likely boundary to investigate |
|---|---|
| Field absent from the UPDATE sent by bgpinjector | Fixture/API/encoder |
| Present toward XR, but absent or changed in XR's mirrored UPDATE | XR acceptance, route processing, or Route Mirroring behavior |
| Present and correct in the embedded UPDATE, but absent/wrong in GoBMP JSON | GoBMP parser/decoder or output schema |
| GoBMP JSON is correct, but downstream consumer lacks it | Publisher, topic mapping, or consumer |
| No Route Mirroring message arrives | XR BMP/Route Mirroring configuration, peer selection, direction, or BMP transport—not a field decoder issue |

When decoding a bandwidth, flag, or nested TLV, retain the exact TLV hex bytes
and document the conversion used. For example, BGP-LS link bandwidth TLVs
1118–1120 are defined by [RFC 8571](https://www.rfc-editor.org/rfc/rfc8571.html),
with bandwidth representation and units specified by [RFC 7471](https://www.rfc-editor.org/rfc/rfc7471.html#section-3).
Do not infer a parser defect from an XR `show` rendering alone when the
embedded UPDATE is available.

## Issue creation workflow

Create one GoBMP issue per independently actionable defect, not one issue per
fixture and not one issue per field when the fields share the same decoder
defect. Before creating an issue, search existing open issues for the same root
cause to avoid duplicates.

Each issue should include:

- A concise title naming the affected BGP-LS NLRI/attribute and behavior.
- GoBMP version/commit and the environment versions needed to reproduce.
- Fixture filename and SHA-256.
- Exact injection command and sanitized HTTP response.
- Expected semantic value, observed GoBMP value, and the raw embedded UPDATE
  TLV bytes.
- XR's received-route output and evidence that the BMP Route Mirroring message
  arrived.
- Applicable RFC and section when the wire format or semantic definition is
  relevant.
- A clear classification: confirmed GoBMP issue, confirmed injector issue,
  XR behavior, or still unresolved.
- A small acceptance criterion, such as “decode TLVs 1118–1120 as IEEE
  single-precision bandwidth values in bytes per second and preserve the
  expected semantic values.”

Do not file a GoBMP decoder issue when the field is missing from the embedded
UPDATE. If evidence is incomplete, create a local follow-up note instead of
guessing which project owns the defect.

```markdown
## Summary

GoBMP decodes `<field/TLV>` as `<observed>`; expected `<expected>`.

## Reproduction
```

## Test completion checklist

- [ ] One fixture was injected per isolated run.
- [ ] Fixture, request response, and fixture hash are saved.
- [ ] BGP and BMP session state was recorded before and after.
- [ ] XR received-route output was saved.
- [ ] GoBMP pre-decode hex logs contain the common header, per-peer header,
  and Route Monitor or Route Mirror body for the route under test.
- [ ] The embedded BGP UPDATE and relevant TLV bytes were identified.
- [ ] A PCAP was saved if the GoBMP hex evidence was incomplete or transport
  behavior needed inspection.
- [ ] GoBMP JSON and logs for the run were saved.
- [ ] Expected versus observed values were compared field by field.
- [ ] Each finding is assigned to a component only when the wire evidence
  supports that conclusion.
- [ ] Independent confirmed defects have separate, non-duplicate GoBMP issues.
- [ ] The public evidence bundle is sanitized.

## From manual tests to automation

For validator-v2 integration, keep each fixture's injection request and
expected GoBMP output contract together, then automate the stable assertions:

1. Submit one fixture to `/v1/routes`.
2. Match the resulting GoBMP record by NLRI identity, peer, and time window.
3. Compare only fields explicitly declared by that fixture's expected contract.
4. Store GoBMP's pre-decode BMP hex logs when a test fails or when the fixture
   is designated as a wire-format regression case. Retain a PCAP when logs are
   incomplete or transport behavior is under test.
5. Report a structured mismatch with the fixture, field path, expected value,
   observed value, and evidence paths.

Automatic issue creation should follow the same evidence threshold as manual
triage. It should group findings by root cause, check for existing issues, and
create separate issues only for independently actionable, confirmed GoBMP
defects. This keeps the test output reproducible and the resulting work
parallelizable without turning one run into a speculative issue dump.
